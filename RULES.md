# RULES.md: hard rules for every agent (read before touching any code)

These rules override convenience. If a task seems to require breaking one, STOP and ask the human lead first, and log the question in plans/03-decisions.md.

## 1. Launchbase core: extend, never replace
Protected (do NOT rewrite, replace, rename, or bypass):
- The existing auth system: JWT login, password hashing, token creation/validation, and the two token scopes (/app and /internal).
- The staff mechanism: the users.is_admin flag, `uv run manage.py create-user --admin`, and internal-scoped tokens. Staff are never created through sign-up.
- The /app vs /internal API surface separation.
- The stack: FastAPI, async SQLAlchemy, Postgres, Alembic, pytest. No Supabase, no other ORM, no other auth provider or auth library.
- The generated API client flow (orval, `npm run generate`). Never hand-write fetch calls to our own API.
- The front-end stack in app/, internal/, site/ (TanStack Start, shadcn/ui).
- Existing endpoints' behaviour and response shapes: don't break them; extend them additively.

Allowed (additive changes):
- New models, migrations, routers, services, schemas, dependencies, and tests that follow the existing users resource pattern.
- Small, minimal edits to core files when strictly needed (e.g. registering a router, adding a nullable column, adding a sign-up endpoint that reuses the existing hashing and token code).
- Rebranding user-facing strings (every "Launchbase" must go by the end).
Every edit to a core file must be minimal, logged in plans/03-decisions.md with the reason, and committed on its own with a clear message.

## 2. Naming safety
- `is_admin` = PLATFORM STAFF. Never use it for customer org permissions.
- Org roles (owner / admin / member) live in the membership table and use clearly different names (e.g. org_role, require_org_admin).
- Never reuse a staff dependency in a customer route, or the reverse.

## 3. Tenancy (highest priority)
- Every customer query is scoped by organization_id derived from the authenticated user's membership, NEVER from a client-supplied org id alone.
- Check roles in the API (dependencies/services), never only in the UI.
- Cross-org access returns 404 (or 403 where the user is a member but lacks the role); never reveal that another org's object exists.
- Every new endpoint ships with tests covering: another org's ID, wrong role, non-lead approving, suspended org.

## 4. Launchbase conventions
- Python: `uv run` / `uv add` only. Never plain python or pip.
- Alembic: autogenerated migrations only; review them before committing.
- No enums in models (use strings + validation).
- Services flush; routers commit.
- After any API change: run `npm run generate` and commit the regenerated client.
- Where the brief and a Launchbase AGENTS.md disagree, the brief wins (tests are REQUIRED).

## 5. AI rules
- Pydantic AI with output_type = Pydantic models. Never ask for JSON in the prompt and parse a string.
- Model: gemini-3.5-flash-lite. GOOGLE_API_KEY only via API settings from api/.env. Never expose it to the browser, never commit it.
- AI output goes to the form only, never straight to the database.
- AI failure (timeout, 429, down) must never break planning; the UI explains in plain words.
- Every AI call is recorded per organization with success / failure / rate-limited.
- Tests use TestModel / FunctionModel. `uv run pytest` must pass with no key and no network.

## 6. Scope
- Out of scope, do NOT build: billing, real email (verification/reset), SSO/social login, GitHub integration, notifications, deployment.
- Optional AI extras: at most one, only after the core is done and verified.
- Don't add features, dependencies, or refactors that weren't planned. Log scope ideas in plans/06-cut-list.md instead.

## 7. UI work
- Before building any UI phase, read plans/09-ui-skills.md and the chosen skills it lists, and apply them.
- Skills and design preferences never override this file: no new UI framework, component library, or styling system, and no hand-written fetch calls to our own API.
- Every screen has loading, empty, error, and forbidden states where relevant. No dead buttons.

## 8. Process and tracking
- Plan before code. No product code before the human approves the plan.
- Work in the phase order and timeline defined in plans/00-master-plan.md and plans/10-dev-flow-and-timeline.md. Don't jump ahead to a later phase.
- Follow the per-phase working loop in plans/10-dev-flow-and-timeline.md.
- Small commits. The repo must never be left broken at session end.
- Tick checklist items only when verified (tests pass or manually checked).
- Update logs/SESSION_LOG.md at the end of every session.
- Every change is recorded in plans/07-change-log.md and, if it affects structure, plans/08-codebase-map.md, in the same commit as the change. An unlogged change counts as unfinished work.
- Never commit secrets (api/.env). Remove any dead code you leave behind.
- When corrected by the human, add a rule here or to AGENTS.md "Lessons learned".
